*A field note on thirteen releases where the code kept turning out to be right and the sentence describing the code kept turning out to be slightly wrong -- a pattern I only trust myself to report because I went and applied the same standard to this piece.*

## A command that returns nothing, and the audit that grew out of it

I want to start with the same thing that started this whole span, because it's the cleanest demonstration I've got of the rule this article ends up arguing for: check the artifact, not the note about the artifact. `docker run --entrypoint trelix-mcp ghcr.io/sairam0424/trelix:3.2.1 --help` returns exit code 127 -- command not found. Not a stale tag, not a typo. The published 3.2.1 image never contained `trelix-mcp` at all. The builder stage copied core `trelix` and stopped there, and `.dockerignore`'s blanket `packages/` exclusion would have blocked the MCP package even if someone had remembered to add the `COPY` line. Sitting right next to it, unrelated: the published `trelix-mcp` console script ignored every flag you gave it -- `--help`, `-h`, `--version`, all of it -- and just silently launched the real MCP stdio server instead.

I didn't find either of those by reading source. Nobody could have. You find them by installing what actually got published and running it, which is a more expensive habit than reading a diff, and also the only one that would have caught this.

That's v3.2.2, and it's where the thirteen-release span in this piece starts -- 2026-08-26 through 2026-09-25, picking up the day after the last article in this series left off at v3.2.1. v3.3.8 is where it ends: tagged, pushed, marked "Latest," and -- I checked this one directly rather than trusting anything written about it -- live on PyPI right now.

## What actually changed, underneath the version numbers

The last piece in this series had a single throughline: a green test suite that never touched the bug it claimed to cover. A `MagicMock` standing in for an embedder. An all-ones attention mask making masked and unmasked math identical. A unit test that had quietly become the bug's own specification. That defect class hasn't vanished -- I'll walk through where it recurred -- but it stopped being the main story here, and I think the reason it stopped is worth sitting with before I get into the specifics.

The response to catching those defects graduated from "write a regression test" into "build a system that makes this whole class of defect structurally unable to reach a tag again." That's the first thing. The second thing is quieter, and honestly the one I find more interesting to report: almost everything genuinely new in this span -- a diagram connector, an MCP protocol upgrade, a retriever-caching fix, a compression provider, an audit-log pruning mechanism -- held up when I checked it against the actual source. What drifted instead was the layer just above the code: a class the CHANGELOG renamed and never caught up to, a performance number with no artifact behind it anywhere, a guarantee that promises slightly more than the code delivers. If the last piece was "the code lied to the tests," this one is closer to "the code is right, and the sentence about the code keeps being slightly wrong" -- which sounds like a smaller problem, and I've come to think it is one, but only because it's a more mature failure mode that shows up once the cruder one has already been shut off.

## The manual audit that automated itself

v3.2.2's fixes were correct and, on their own, unremarkable. What I actually want to tell you about is what the team did next, because it's the best answer I've seen in this whole series to the question "okay, you caught it once by hand -- now what?"

Two releases later, v3.2.3 took the exact manual pass that had just caught those two live defects and turned it into permanent CI. There's a real-subprocess E2E suite now that spawns `trelix-mcp` as an actual OS process talking real stdio JSON-RPC. Fresh-venv installs of all four published packages. A `smoke-test-built-artifacts` job that `release.yml`'s `publish` job is hard-gated on. A Docker check that `trelix-mcp` is actually present inside the built image. A Helm-lint check that the rendered image tag matches `Chart.yaml`. The same release also fixed a real, separate bug along the way -- a `LIKE`-wildcard escaping gap in `path_filter`-scoped BM25/grep queries, where an ordinary underscore or percent sign in a directory name was being read as a SQL wildcard. Not injection, since the queries were already parameterized -- just a distinct semantics gap, closed with a shared `escape_like_pattern()` helper and an `ESCAPE '\'` clause.

The centerpiece, and the part I spent the most time actually reading rather than skimming, is `scripts/verify_release.py` -- 742 lines, five independent check functions, each returning a list of failures and never raising, so one category's bug can't hide another's results. `check_pypi_installs` does a fresh venv per package and a real `pip install <pkg>==<version>`, then a real console-script and import smoke test against the version string. `check_docker_images` pulls both the plain and `-local` tags and runs the exact `--entrypoint trelix-mcp --version` command that returned 127 on the unpatched 3.2.1 image -- and I want to flag that detail specifically, because this check exists for the sole reason that this exact command failed once, silently, in production. `check_helm_chart` checks out `v<version>` into a throwaway `git worktree` -- never the caller's own working tree -- and runs `helm lint`/`helm template` across all three store backends. `check_github_release_binaries` downloads and `file(1)`-checks all four platform assets and executes whichever one matches the current host, printing rather than silently skipping when it can't run a foreign-arch binary. `check_security_audit` runs `pip-audit --format json` on all four packages in a fresh venv and separately scans every wheel for `.env*`, `.git`-path, or `credential`/`secret`-named files that should never ship.

v3.2.4 wired all of it permanently into CI, via a 99-line `.github/workflows/verify-release.yml` that I read line by line: it waits for both `release.yml` and `docker-publish.yml` to go green for a pushed tag, runs `verify_release.py` automatically, and posts a PASS/FAIL comment -- with the manual command still available for ad-hoc re-runs. It uses `env:` passthrough rather than `${{ }}` shell interpolation, matching `docker-publish.yml`'s own injection-avoidance convention, which is the kind of small consistency detail I only notice because I went looking for it. v3.2.5, the same day, closed a smaller instance of the identical gap-class: the frozen PyInstaller binary's embedder error message told users to `pip install 'trelix[local]'`, which does exactly nothing for a binary that never touches the host's Python or pip in the first place.

I ran the one check in this whole piece that isn't source-reading -- `curl https://pypi.org/pypi/trelix/json`. `info.version` comes back `3.3.8`. The release history lists 3.2.2 through 3.2.5, then jumps to 3.3.0, 3.3.5, 3.3.6, 3.3.7, 3.3.8 -- 3.3.1 through 3.3.4 are conspicuously absent from PyPI's own list. I take that to mean they likely never went out as standalone PyPI releases rather than anything more dramatic, but I didn't dig further, and I'd rather flag that gap than paper over it. `trelix-mcp` is confirmed in lockstep at 3.3.8 too, wheel and sdist both uploaded 2026-09-25T09:54 UTC. Of everything in this piece, that's the one claim I trust most, precisely because it's the one thing here that isn't me reading a source tree -- it's a live number pulled straight from the index.

## v3.3.0: a minor version that actually earns the word "breaking"

Everything else in this span is a patch. v3.3.0 is the one deliberate minor bump, with four real breaking changes, and I want to give it credit for that framing even in the same breath as I correct its own documentation.

The four changes: the Python floor moved to `>=3.12` everywhere; the `TRELIX_RETRIEVAL_FLARE_MAX_ITER` env alias was removed outright, with zero remaining references anywhere outside docs; `AWS_REGION` is now hard-required for the Bedrock backend, raising `ValueError` where it used to silently default to `us-east-1`; and the Anthropic backend now silently no-ops on a `temperature` argument instead of forwarding it, logging a one-time warning instead of just dropping it invisibly. Those last two are, by my own read, exactly the two changes most likely to actually break someone's deployment on upgrade -- and, by my own read of `docs/migration/v3.2-to-v3.3.md`, they're the two the migration guide doesn't mention at all. The doc covers three of the six real changes and its own closing section says the LLM-provider and MCP changes are "not yet released" -- when in fact they shipped the same day, under the same tag. If you're the kind of person who upgrades by reading the migration doc instead of the CHANGELOG, this is the release where that habit would have cost you.

Here's a naming error I think is worth stating plainly, because it's the kind of thing that costs you real debugging time if nobody tells you: the CHANGELOG calls the new reasoning-content type `ReasoningBlock`. I went and checked `src/trelix/llm/client.py` directly -- line 29 -- and the actual class is named `ThinkingBlock`. A repo-wide grep for `ReasoningBlock` across `src/`, `packages/`, and `tests/` returns nothing. What actually ships is `ChatResponse.thinking_blocks: list[ThinkingBlock]` plus a back-compat `ChatResponse.thinking: str | None`, and both the Anthropic and Bedrock backends build `ThinkingBlock` instances correctly, including the previously-dropped `redacted_thinking` variant. If you grep for the CHANGELOG's own name, you'll get nothing back. Use `ThinkingBlock`.

Separately -- and this is the part of v3.3.0 I'm most confident in -- MCP gained SEP-2322 support: `AgentResult.needs_input`, set only on an explicit `CLARIFY` action from the agent loop, lets the `ask_agent` MCP tool wrap an `ElicitRequest` inside an `InputRequiredResult` when the agent genuinely needs clarification, resuming later through a dedicated answer-extraction path. It's additive; non-elicitation callers see no change. But even here, where I trust the mechanism completely, the release's own note about it doesn't fully hold: Bedrock's `stream()` method got a fix for dropped reasoning deltas, and the CHANGELOG describes it as fixing dropped reasoning *and* tool-use deltas together, "now logged at debug level instead of vanishing untraced." Reading the actual diff, only the `reasoningContent` half shipped. There's no branch at all for `toolUse` deltas -- a `contentBlockDelta` carrying incremental tool-call argument fragments still falls through with zero logging, exactly as it did before the fix. It's a small gap. It's also exactly the kind of gap you only find by reading the diff instead of the note describing it, which by now is the whole point of this piece.

## The same bug shape, one layer deeper

The prior article's four-instance spine -- a green suite that never exercised the defect it claimed to cover -- recurs here too, except this time it's the product of a deliberate audit rather than something someone happened to trip over. A correctness sweep hunting one specific bug pattern, qualified-name collisions, pulled 19 independently confirmed defects across seven subsystems in v3.2.4 alone.

Two of them are the same shape at different altitudes, and I think that's worth walking through rather than just listing. The installed tree-sitter-java grammar emits `formal_parameters`/`formal_parameter` for a Java record's component list, not the `record_parameters`/`record_component` node types the extractor had assumed -- so every record's component list had been rendering empty. The fix shares one `_extract_type_list_edges()` helper across six call sites instead of patching the single spot that happened to get noticed. Rust had the mirror problem: `use foo::{Alpha, Beta}` -- the dominant real-world Rust import form -- fell through to a generic single-name fallback because the code checked for `use_tree_list`/`use_tree` node types tree-sitter-rust doesn't actually emit; the real types are `scoped_use_list`/`use_list`. Before the fix, that path would have produced the literal string `"{Alpha, Beta}"` as a bogus import name, which is the kind of thing that's obviously wrong the moment you look at it and invisible the moment you don't.

One layer up, in the federation retriever, `make_scip_symbol_id()` hashed only `(package, version, qualified_name)` -- so two files sharing a qualified name, like two `def main()` entry points in different modules, collided, and the second one was silently dropped via `INSERT OR IGNORE`. The fix folds `file_path` into the hash. And here's the part I actually find encouraging rather than embarrassing: a fix in v3.3.4's chunker -- where oversized symbols had their excess body silently discarded and replaced with a truncation marker, unrecoverable by retrieval -- created a *new* collision surface one release later, because multiple chunks could now share one `symbol_id`, and the fusion/dedup layer's key hadn't yet caught up. v3.3.5's own fix docstring says so directly: this is the same defect class recurring one abstraction level down from a bug they'd just fixed days earlier, in code the same engineers had just touched. That's the honest version of "we fixed it" -- not zero recurrence, but naming the recurrence the moment it happens instead of treating each instance as a fresh surprise.

There's a separate research artifact I want to mention because it does something I don't often see: a 94-agent chunking-strategy study found trelix's one-symbol-per-chunk approach underperforming alternative strategies by 3.57–5.64 percentage points of exact-match accuracy against a real published benchmark -- and then rated its own recommendation "LOW-MEDIUM confidence a full redesign is worth building right now," specifically because a redesign would break the 1-chunk-to-1-symbol cardinality assumption baked into the reranker and graph-context code, which it describes as "the exact class of bug this session already found three separate times in adjacent code this same week." A research doc citing its own team's bug history as the reason to be cautious about its own conclusion is a genuinely unusual thing to read, and I'd rather see that than either a redesign shipped on a hunch or a study that ignores its own team's track record.

## The GitHub App: real review, not a Marketplace listing, and one question I couldn't close

There are two real, shipped ways to get trelix's review on a PR, and both post a check literally named "trelix Code Review." One is a GitHub Actions workflow that trusts nothing beyond the repo's own `GITHUB_TOKEN`. The other is a standalone GitHub App -- TypeScript/Express, webhook-driven, zero workflow YAML required in the installing repo -- and I confirmed it's live right now on Railway, production environment, deployed from commit `ac94e1c` on `main`, instance status RUNNING. The tradeoff is exactly what it looks like on the label: the Actions path trusts nobody, the App path is more convenient and asks you to trust a real third party with real permissions on your repo.

It is not, and shouldn't be described as, a Marketplace app, and I appreciate that the project says so about itself rather than making me go dig it up. `infra/github-app/README.md` states it outright, and I'm quoting rather than paraphrasing: "Not claimed: GitHub Marketplace listing. This App is installable and hardened, not Marketplace-verified." `docs/ROADMAP.md` lists the listing as an explicit open backlog item, gated on roughly 100 installations before GitHub will even review it -- an adoption gate, not an engineering one.

I read the security posture underneath at the file level rather than taking it on faith, and it holds up: webhook signature verification uses `timingSafeEqual` via `@octokit/webhooks-methods` and rejects unauthorized requests before the payload body is even read; installation tokens are minted and cached per-config in a `WeakMap`, with JWT-mode auth correctly *not* cached; PR checkouts clone into a temp workspace and fetch `refs/pull/<n>/head` -- the correct ref for fork PRs -- with the token passed only via a `GIT_ASKPASS` environment variable, never in a URL, argv, or git config where it could leak into logs; and there's a 25MB payload cap applied *before* signature verification, which is the only defense against an oversized unsigned body. As of v3.3.8, a review that times out or crashes now always posts a completed Check run instead of leaving the PR with no status at all -- `timed_out` when the process was SIGTERM'd, `neutral` otherwise. That's a real fix for a real silence-on-failure gap, and a good instinct for a system whose entire value proposition is a status check people are supposed to trust.

Here's the part I want to be careful not to resolve just because a clean ending would feel better: there's a documented, not-yet-confirmed-resolved concern that the App's own review of trelix's own large codebase has been getting SIGKILLed before indexing finishes, suspected to trace back to `review-runner.ts`'s hardcoded 5-minute `INDEX_TIMEOUT_MS`/`REVIEW_TIMEOUT_MS`. I checked those constants directly -- unchanged at 5 minutes, in this span and since. But I also checked every CHANGELOG line, every ROADMAP line, and the git log for any commit connecting those two constants to an actual SIGKILL-during-self-review incident, and found nothing. The only `SIGKILL` mentions anywhere in the App's code concern a completely different scenario -- OOM-killed processes leaving stale temp workspaces behind, handled by a `sweepStaleWorkspaces()` cleanup at boot. So: the timeout constants are exactly as short as the concern says, and nothing in the repository actually substantiates that they're the cause, or that the failure is even still happening. I'm leaving this as an open question because it is one. I don't want to confuse it with a different, already-closed issue in the same App: a missing `TRELIX_EMBEDDER_PROVIDER=azure` env var on Railway, which caused indexing to silently fall back to a never-installed local embedder and fail. That one's fixed, 2026-09-22, via a deployment config change rather than a code change. Two unrelated bugs at two unrelated layers -- only one of them is actually closed.

## Diagrams as text: the .drawio connector

v3.3.6 shipped a fifth connector alongside Jira, TestRail, Xray, and Linear: `trelix connector sync <repo> diagram`, for local `.drawio` files. The mechanism turned out to be more mundane than I expected, in the good way -- every shape in a drawio file's mxGraph XML carries its label in a plain `value="..."` attribute, and every edge is an explicit `<mxCell edge="1" source=... target=...>`, so the whole diagram is fully describable as text without any vision model at all. The connector truncates the XML to 20,000 characters and sends it through the same text-only chat client every other LLM call site in trelix already uses. Raster images -- PNG, JPG -- are explicitly out of scope, and there's no glob or handling for them anywhere.

v3.3.7 fixed a real bug in the fallback path that I think is worth calling out on its own: when captioning failed, the connector used to discard the diagram's actual content entirely and just report a character count. Now it regex-extracts real `mxCell value="..."` shape labels, HTML-unescapes before stripping inline tags (order matters here, since drawio escapes attribute values, so entities have to decode before tags can be safely stripped), de-duplicates in first-seen order, caps at 50 labels, and only falls back to the old length-only message when literally zero labels exist. It's a small fix, but it's the difference between "the diagram failed to caption, here's 4,200 characters" and "the diagram failed to caption, here are the 12 real shape labels it actually contains" -- a useless fallback versus a usable one. There's no diagram-specific config or env var; it rides whichever LLM provider is already configured, and the artifact linker treats a diagram exactly like a Jira ticket -- same edge shape, same matching logic, no special-cased code path.

## Performance: real numbers, and one I won't repeat

v3.3.8 fixed a real inefficiency I'd recommend without reservation: `trelix-mcp`, the LangChain retriever, and the LlamaIndex retriever all used to rebuild a fresh `Retriever` object on every single call. They're cached now -- module-level with a lock in the MCP server, correctly invalidated on reindex, per-instance in both framework adapters. What I can't recommend repeating is the specific number attached to it. The CHANGELOG cites a "24.5x–52.7x measured speedup," and I went looking for where that number actually comes from. It appears nowhere except the CHANGELOG's own prose -- not the commit message I pulled directly, not the PR, not any test. The commit itself says only that three consecutive calls in one session took 13-16 seconds, then 5, then 5, with zero warm-up benefit -- no multiplier anywhere, and no recorded post-fix warm baseline to derive one from. The fix is real. The multiplier isn't backed by anything I could find outside the CHANGELOG's own unsupported prose, so I'm not going to be the one who repeats it as measured.

The rest of this theme holds up better on inspection. `trelix-mcp` and the graph community-detection code's use of `nx.pagerank` now catch `ImportError` and degrade to a uniform-score fallback instead of crashing, because scipy is only imported lazily on first call and the frozen binary deliberately excludes it -- a real crash class closed with two small, defensive catches. Qdrant gained int8/binary quantization support, with one small flag worth naming: the commit claims verification against `qdrant-client==1.19.0`, but the lockfile currently pins 1.18.0. I don't think that's a contradiction so much as a dev-venv version that never made it into the lockfile -- but I also can't independently confirm it, so I'm treating "verified against 1.19.0" as unconfirmed rather than false. A direct Cohere embedder landed using `cohere.ClientV2` rather than routing through Bedrock, with a 96-item batch limit.

And an abstractive compression provider shipped with a real gap between what the CHANGELOG promises and what the code actually guarantees -- one I think is worth stating carefully. The CHANGELOG says the signature *and* docstring line are "always kept byte-for-byte." The actual `_must_keep()` logic only locates and preserves the declaration line itself; the docstring on subsequent lines gets forwarded to the LLM as context with no verbatim guarantee at all, and can come back paraphrased. The test suite's own docstring gets this right where the CHANGELOG doesn't -- "the declaration line is ALWAYS kept verbatim," singular. If you're relying on this feature to preserve a docstring exactly, don't. That's what the separate extractive compressor actually does.

## Security: two CRITICAL CVEs, and an audit trail that undersells itself

The litellm floor moved to `>=1.90.2`, closing two CVEs the project's own pins describe as CVSS 9.8 -- a Host-header authentication bypass and an unauthenticated SSTI leading to RCE -- plus a third SSRF issue via nested `user_config`. I can confirm those citations are in the repo's own dependency comments; I couldn't independently cross-check the CVE IDs against GitHub's live advisory database from where I was working, so I'm attributing the "two CRITICAL, CVSS 9.8" framing to trelix's own release notes rather than something I verified myself against an outside source. Separately, `pydantic-settings` CVE-2026-58203 was patched by a floor bump, and I confirmed the vulnerable feature -- `secrets_nested_subdir` -- was never actually called anywhere in the codebase, so this one was zero real exposure even before the bump. A clean case of patching a dependency that was never actually exploitable through this code, which is a nice thing to be able to say plainly.

The most substantial security addition is `trelix audit prune` -- a real hash-chain watermarking implementation for pruning old audit-log rows without breaking chain verification, with a `--dry-run` mode I confirmed isn't wired into any in-process scheduler. What struck me reading it is that the module's own docstring is more conservative than the marketing framing around it: it states plainly that this is "tamper-evident, not tamper-proof," and it enumerates exactly which tamper shapes remain undetectable -- a total wipe that also clears SQLite's own internal sequence table, for instance. A security feature whose own documentation undersells its guarantees relative to the copy around it is the rare direction I'm genuinely happy to see the drift run.

## The smaller stuff, briefly

Two releases of CLI/API/extension hardening are worth a fast pass, even in a piece this long. v3.3.1 fixed four real VS Code extension bugs: a JSON.parse crash whenever the MCP client returned plain text instead of JSON, a path escape hatch for GUI-launched editors whose PATH excludes pip/uv, inline symbol links in chat responses, and a CodeLens replacing a global QuickPick for blast-radius visualization. v3.3.7 fixed a `.vscodeignore` gap that had been shipping a local vector database file and gigabyte-plus of sourcemaps inside the packaged extension -- `vsce` ignores `.gitignore` entirely once `.vscodeignore` exists, so the two files having drifted apart had real, shippable consequences. The same release moved four CLI/REST failure modes from raw tracebacks or bare 500s to labeled, structured errors: `eval`/`eval-synthesis`/`migrate-vectors` now print one-line labeled errors instead of stack traces; a missing golden file for synthesis eval now raises `FileNotFoundError` instead of silently returning zero-filled metrics; the REST API's `DimensionMismatchError` and `ImportError` now return structured JSON 500s instead of Starlette's plain-text default; and static-token auth now checks `Authorization: Bearer` independently of `X-Trelix-Api-Key`, via `hmac.compare_digest`, closing a path where the Bearer header was silently ignored.

## The pattern I kept running into, and the one I had to run on myself

I want to name the thread across all these corrections rather than let them read like scattered nitpicks, because by the time I'd found the fourth or fifth one I realized they were all one thing: `ReasoningBlock` versus `ThinkingBlock`, the half-shipped `toolUse`-delta logging claim, the unaudited 24.5x-52.7x figure, the docstring-verbatim overstatement, a migration guide stale relative to its own release date, a `docs/WHY_TRELIX.md` version-scope stamp still reading v3.3.7 while the package is at v3.3.8 -- none of these are bugs in the code. Every single one is the layer just above the code: the sentence describing what the code does, written slightly faster or slightly more optimistically than the code itself actually justifies. That's a different failure mode than a `MagicMock` hiding a broken embedder, and I've come around to thinking it's a sign of health rather than decline -- it only becomes the dominant story once the release-verification discipline earlier in this span had already closed off the cruder failure of a defect reaching a tag at all.

And I'd be leaving something out if I didn't say this plainly: it's also exactly the standard this piece itself needed applied to it. I only trust the corrections above because I went and checked the sentence against the source rather than against the intent, on every theme I touched, including the ones where I was tempted to just repeat what the release notes said and move on.

## What v3.3.8 actually means if you're upgrading today

If you're coming from anywhere before v3.3.0, read the CHANGELOG for that release specifically, not the migration guide -- the guide is missing the `AWS_REGION` requirement and the silently-dropped `temperature` parameter, which are the two changes most likely to actually break your deployment. If you're grepping the codebase for the reasoning-content type, look for `ThinkingBlock`, not `ReasoningBlock`. If you're evaluating the retriever-caching fix, trust the mechanism and not the specific multiplier attached to it. If you're relying on abstractive compression to preserve a function's docstring exactly, it doesn't -- only the declaration line is guaranteed verbatim. And if you're deciding between the GitHub App and the Actions workflow for PR review, both post the same "trelix Code Review" check, but only one of them asks you to trust a third party -- and if you run the App against a codebase the size of trelix's own, know that a timeout-related self-review concern from a week ago hasn't been confirmed fixed, or confirmed to still be happening either.

None of that is a reason not to upgrade. The live PyPI check I ran directly -- not read, not paraphrased, actually executed -- confirms v3.3.8 across all four packages, published in lockstep on 2026-09-25. The release-verification infrastructure built in v3.2.3 and v3.2.4 means that check itself, along with a Docker `--version` smoke test and a Helm chart lint, now runs automatically against every tag before it's allowed to publish, which is a meaningfully different guarantee than the source tree alone ever gave anyone. What changed across these thirteen releases isn't that trelix stopped shipping defects -- the parser sweep alone found 19 of them in a single release. What changed is that the mechanism for catching what a green test suite misses stopped being one person doing it once, by hand, out of frustration, and started being a system that runs on every tag whether or not anyone remembers to ask. The part that hasn't caught up yet is the sentence describing the fix -- which is a smaller problem to have than the one this project started with nine weeks ago, and a more honest place for me to end this than pretending that layer isn't still there at all.
