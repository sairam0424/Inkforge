I spent my first day on a new team grepping through 80,000 lines of code trying to find where authentication worked.

Four hours. Three teammates interrupted. Twelve dead ends. The code was fine — well-written, organized, reasonably documented. The tooling was the problem. I was using grep to understand something that wasn't a text search problem. Code has structure: call edges, import chains, type hierarchies, abstract syntax tree relationships. Grep ignores all of it.

That afternoon I started thinking about what a better tool would look like. It took about two years of evenings to build it properly. I called it trelix.

## Why Grep Is the Wrong Tool for Understanding Code

Most of the tools we use to navigate code — editors, grep, ctags, language servers — were designed for writing code. They're excellent at navigating to a known destination. You know the function name, you jump to it. That's not understanding.

Understanding is answering "how does the request lifecycle work end-to-end?" or "what depends on this module if I change it?" when you don't already know the answer. For those questions, grep's fundamental limitation is that it treats your codebase as a document. It finds strings. Code isn't a document — it's a graph.

Functions call other functions. Modules import other modules. Classes extend other classes. When you ask "how does authentication work?", the answer is a traversal of that graph from a semantic entry point, not a search for the string "auth" in file names.

Vector search solves part of this. Semantic similarity gets you to the right neighborhood without knowing exact tokens. But pure vector search misses the structure. It doesn't know that `UserRepository.get_by_token()` is always called by `AuthMiddleware.verify()`, which is wired into every protected route. That relationship is in the call graph, not in the embeddings.

trelix uses both.

## What trelix Does

trelix is an open-source code intelligence engine. It indexes any repository with Tree-sitter AST parsing, stores everything in a single SQLite file, and answers natural-language questions about your code using hybrid search.

```bash
pip install "trelix[local]"   # no API key needed
trelix index ./my-repo
trelix ask ./my-repo "how does authentication work?"
```

The index contains every symbol extracted via Tree-sitter (functions, classes, methods, their bodies and line spans), directed call and import edges, a BM25 FTS5 index over chunk summaries, and an HNSW vector index via sqlite-vec. Everything in `.trelix/index.db`. No Docker. No Postgres. No Redis.

When you ask a question, a 3-tier adaptive router decides how to answer it. Simple factual queries skip retrieval entirely and go straight to the LLM. Most code queries get classified into one of eight intents (symbol lookup, feature flow, dependency map, blast radius, and four others) and routed to the appropriate combination of retrieval legs. Complex multi-part queries get decomposed into sub-queries, run independently, and merged.

Results from all active retrieval legs are fused via Reciprocal Rank Fusion — a robust ranking method that uses position rather than raw scores, so BM25 results and cosine similarities can be meaningfully combined — before being assembled into the LLM context window.

## Zero Infrastructure by Design

This was a deliberate choice that I keep being glad I made.

Most code intelligence tools require running a vector database, a relational database, and often a separate API server. That's meaningful infrastructure to operate just for a developer tool. trelix's default is a single SQLite file: sqlite-vec handles HNSW vector search, FTS5 handles BM25, and the same file stores symbols, call edges, import edges, and file hashes for incremental updates.

For teams with larger codebases, LanceDB gives 3-5× faster vector inserts at 100k+ chunks (especially on ARM/Apple Silicon), and Qdrant handles 500k+ chunk deployments. But the default gets most developers all the way to production without touching infrastructure.

The offline default matters for a different reason too: a lot of the most interesting codebases are internal and shouldn't leave the network. `pip install "trelix[local]"` and you have hybrid code search that never calls an external API.

## How Search Actually Works

trelix has seven retrieval legs that all run on the same query and contribute to the fused result:

**Contextual BM25** — FTS5 full-text search over chunk summaries generated by an LLM at index time. Finds exact symbol names and error messages even in semantic queries.

**Vector ANN with HyDE** — HNSW approximate nearest neighbor search. For abstract questions, HyDE first generates a hypothetical code answer and uses that as the query vector, improving recall significantly on questions like "how does session timeout work?"

**Grep** — exact and regex search. Sometimes the right answer is just finding a specific error code or URL pattern exactly.

**Code Property Graph BFS** — starting from the top results found by vector and BM25 search, BFS traversal follows call edges and import edges to surfaces structurally related code. This is what finds `AuthMiddleware.verify()` when you search for "session token validation" — the semantic search finds the session manager, and graph traversal follows the call chain to the middleware.

**File-summary semantic** — RAPTOR-style search over LLM file summaries. Answers questions at the architecture level: "what files handle payment processing?"

**SPLADE-Code** — sparse+dense hybrid retrieval. Vocabulary expansion for queries that need it.

**Multi-granularity** — indexes code at block and statement level simultaneously for queries that need fine-grained precision.

The default setup runs legs 1-4. Legs 5-7 and query-side enhancements (HyDE, FLARE confidence-gated re-retrieval, agentic multi-turn loop) are opt-in via environment variables.

## The Features That Made It Real

I'll be direct about which features changed trelix from an interesting experiment to something I use daily.

**GitHub PR review.** `trelix review --pr owner/repo#42 --post-comments` fetches the diff, retrieves codebase context for each changed hunk, runs an LLM review, and posts findings back to GitHub in a single batched review. The version before this felt academic. This felt like shipping a product. The insight behind it is simple: a code reviewer who hasn't read the codebase gives worse reviews. trelix gives the LLM the codebase context before it reviews the diff.

**Federated search.** `trelix search-all "query"` searches across all registered repositories simultaneously and merges the results. `trelix watch-all` watches all of them for changes with a single file-watcher. For engineers who work across multiple services, this is the feature that reduces the "which repo does this live in?" problem from 10 minutes to 3 seconds.

**MCP integration.** One command and trelix works inside Claude Code, Cursor, Windsurf, and Continue.dev:

```bash
pip install trelix-mcp
claude mcp add trelix -- trelix-mcp
```

Inside the IDE, you can say "index my repo at /path/to/repo, then find how authentication works" and get a contextually rich answer that follows call chains.

**Agentic mode.** With `TRELIX_RETRIEVAL_AGENTIC=true`, trelix enters a multi-turn retrieve→observe→re-retrieve loop. If the first retrieval pass doesn't surface enough context to answer confidently, it reasons about what's missing and queries again. FLARE adds a complementary mechanism: when the synthesis output contains uncertainty markers, it re-retrieves before finalizing.

## What I Got Wrong Building This

I expected the hardest part to be the embedding and retrieval pipeline. It wasn't.

The hardest part was the call-graph resolver. My first version used name-only matching for cross-file call edges. `login()` in file A calls `login()` in file B. This produced a dense, noisy graph with roughly 40% false-positive edges on real codebases. The fix was a 3-priority resolution strategy: try qualified name first (most precise, lowest recall), then type hint plus name, then name-only as fallback. That cut false positives to around 10% while maintaining recall on Python and TypeScript codebases without full type annotations.

The other thing I got wrong was my intuition about where the value comes from. I expected the LLM synthesis to be the differentiating layer. I was wrong. The structural metadata — the call graph, the import graph, the type hierarchy — is where trelix is qualitatively different from vector search over code. Semantic similarity gets you to the right neighborhood. Graph traversal gets you to the right answer. The LLM just presents it clearly.

## How to Try It

```bash
# Offline — no API key, works on any machine
pip install "trelix[local]"
trelix index ./your-repo
trelix ask ./your-repo "how does your main feature work?"

# With OpenAI for LLM synthesis
pip install trelix
export OPENAI_API_KEY=sk-...
trelix ask ./your-repo "explain the request lifecycle end-to-end"

# Inside Claude Code / Cursor (MCP)
pip install trelix-mcp
claude mcp add trelix -- trelix-mcp

# GitHub PR review
trelix review --pr owner/repo#42 --post-comments
```

trelix is MIT licensed, 1,508 tests, and available on PyPI as four packages: `trelix`, `trelix-mcp`, `trelix-langchain`, `trelix-llama-index`. Source at [github.com/sairam0424/trelix](https://github.com/sairam0424/trelix).
